# Fixtures 与外部验证策略
> 规划层｜职责：定义样本从哪来、如何验证、许可与落点，以及读端现实文件的补充策略。｜禁止：复制测试名、记录测试计数、存放历史叙述。

## 0. 策略结论

1. **主路径为“库写端生成 + 外部主流工具核对”**：不再寻找许可难搞的第三方 PDF；每个标准特性对应一条可复现的生成用例（W 层）。
2. **自产样本的证明边界**：只能证明“写端按规范产出，且外部阅读器/工具认可该文件”；**不能证明读端能吃掉现实世界的异形文件**。
3. **PDF 文件一律不入 git 追踪**：仓库只保存生成脚本、样本清单、来源 URL、SHA-256、许可说明等元数据。任何 PDF 文件（W、R、L 三层，含“留档”“冻结”“最小回归件”等名义）都不进索引，不设体积或许可例外。
4. **读端现实性样本仍然保留，但只存在于本地**：R 层由外部工具现场生成；L 层（原 4 个 CC-BY-SA-4.0 样本）改为“本地保留、从索引摘除”。两者都靠清单与哈希在本地复原，不随仓库分发。
5. **缺样本时必须跳过而不是失败**，且报告必须区分 `SKIP(missing-sample)` 与真正 `PASS`；该语义与配套改动登记为待办（见 §5），本轮只写文档。
6. 排序原则：**PDF 标准特性优先，扩展特性次之**；该原则同时写入 `docs/roadmap/README.md` 的「排序原则」。

## 1. 分层（取代旧 L1/L2/L3）

| 层 | 产出方式 | PDF 入仓 | 落点 | 许可与校验 | 用途 |
|---|---|---|---|---|---|
| **W** 写端生成 | 本库 builder 按用例生成 | **不入仓**（`verification.json` 也只留本地） | `target/fixtures/writer/<case>/` | 无第三方权利；文件头标注库版本；用例号、版本、SHA-256 记入清单 | 证明写端产物被外部工具接受 |
| **R** 外部产出、只读 | qpdf、Edge 打印、LibreOffice 等外部工具现场生成 | **不入仓** | `%LOCALAPPDATA%\pdf_engine-fixtures\reader\` | 内容自撰；不随仓库分发，无再分发义务；生产者版本与 SHA-256 记入清单 | 证明读端能吃现实/异形文件 |
| **L** 存量上游样本 | 原 `py-pdf/sample-files` 样本，本地保留 | **不入仓**（从 git 索引摘除，工作区文件保留） | 本地 `tests/fixtures/`（不被 git 跟踪） | CC-BY-SA-4.0；来源 URL 与 SHA-256 入清单 | 读端回归冒烟；文件缺失时用例跳过 |

**旧分层迁移**：旧 L1“自建最小样本”并入 W 层；旧 L2“公开许可真实样本”清单与旧 L3“本地大样本”清单一并删除（不再追许可、不再登记 veraPDF/py-pdf 大文件下载）；旧 L1 中依赖外部编码器的条目改由 W 层“容器 + 外部码流”承载，外部产出部分归 R 层。

**入仓范围**：只允许元数据与脚本——生成脚本、样本清单（`tests/fixtures/manifest.toml`）、来源 URL、SHA-256、许可说明；**任何 PDF 文件都不入仓**，W/R/L 三层同样适用。清单只登记文件的不可变属性，不附二进制；工作区中的 PDF 由 `.gitignore` 的 `*.pdf` 兜底忽略，`!tests/fixtures/*.pdf` 反选例外须随之删除（待办见 §5）。许可只作为来源说明，不再作为“能否入仓”的判据。

## 2. W 层：写端生成用例

### 2.1 生成协议

- **版本戳**：文件第 2 行写入 `% Generated by pdf-engine <version> (<case-id>); do not edit`，同时设置 Info `/Producer (pdf-engine <version>)` 与 `/Creator`。`<version>` 取 `CARGO_PKG_VERSION`，保证可追溯到生成时的库版本。
- **确定性**：固定 `/ID`、`/CreationDate`、`/ModDate` 与对象顺序；同一版本重复生成应得到相同 SHA-256，否则视为用例缺陷。
- **输出**：默认写 `target/fixtures/writer/<case>/<name>.pdf`，不入仓；即使需要人工留档也不进 git，只把用例号、库版本与 SHA-256 登记到清单。
- **结果清单**：每次验证写同目录 `verification.json`，字段至少含 `case`、`library_version`、`pdf_sha256`、`tools[]{name,implementation,version,path,checks,result}`、`deviations`。该文件只留本地，不入仓；可入仓部分仅为汇总后的用例号、版本与 SHA-256。

## 3. R 层：外部产出、只读、永不入仓

R 层的目的只有一个：**读端现实性验证**。这些文件不由本库写出，因此不构成“写端自证”；内容一律自撰，工具只负责生成，产物本地保存，仓库内不出现二进制。

| 用例 | 外部生产者（版本记录方式） | 生成方式 | 读端核对 | 状态 |
|---|---|---|---|---|
| R-01 | qpdf（`qpdf --version`） | `--encrypt` 生成 RC4-128 与 AES-128 两个版本，设置用户/所有者口令与权限位 | 本库读端正确解密、权限位与 qpdf 输出一致；错误口令返回类型化错误；V1 输入口令可打开 | 待执行 |
| R-02 | qpdf（`qpdf --version`） | 对基线文件连续追加修订，包含删除对象、替换对象、新增页面 | 本库读端按 `/Prev` 链取最新对象；旧修订对象仍可访问；页数与 qpdf 一致 | 待执行 |
| R-03 | qpdf + 脚本化破坏（版本随基线） | 截断尾部、篡改 xref 偏移、破坏流长度、缺失 `endstream` | 本库读端给出类型化错误或按策略恢复；不得 panic/OOM；错误前缀与既有过滤器一致 | 待执行 |
| R-04 | qpdf 或 pikepdf（版本记录方式同上） | 生成混合引用（经典 xref + `/XRefStm`）；若工具不支持，只保留 W-04 并由 V1/V3 对照 | 本库读端同时读取两张表、重复对象号以流表为准 | 待执行 |
| R-05 | Microsoft Edge 打印为 PDF（`edge://version`） | 打开本地自撰 HTML（含中文、表格、链接、分页）并打印为 PDF | 真实生产者的页面树、字体子集、链接、页面框可读；文本抽取与 HTML 原文一致 | 待执行 |

| R-07 | qpdf（`qpdf --version`） | `--linearize` 生成真实线性化布局 | 本库读端读取提示表；V1 首屏可见；与 W-05 对照 | 待执行 |

R 层落点与清单：

- 目录 `%LOCALAPPDATA%\pdf_engine-fixtures\reader\`（可用 `PDF_FIXTURE_ROOT` 覆盖）；**不得**出现在任何 git 跟踪路径。
- 每个文件在本地 `manifest.json` 记录：用例号、生产者、版本、生成命令、SHA-256、生成时间、内容版权声明（自撰）。其中可入仓的元数据汇总到 `tests/fixtures/manifest.toml` 的 `reader` 段；PDF 与运行产物均不入仓。
- 失败样例同样保留在本地清单中，便于回归；不得为了“通过”而修改外部产物。

### 4.1 索引摘除后回归基线如何维持

| 场景 | 行为 | 报告状态 |
|---|---|---|
| 本机文件存在且 SHA-256 与清单一致 | 照常执行既有读端用例 | `PASS` |
| 本机文件存在但哈希不符 | 停止该用例并报错，防止静默替换 | `FAIL` |
| 冷环境 / CI 无文件 | 不执行用例，打印缺失文件名与清单 URL | `SKIP(missing-sample)` |
| 清单缺失、哈希格式错误或来源 URL 为空 | 清单本身不合格 | `FAIL` |

维持规则：

- **事实源是清单**：`tests/fixtures/manifest.toml` 随仓库走，记录文件名、本地路径、来源 URL、许可、体积、SHA-256；回归基线以清单为准，不以 git 内容为准。
- **本地复原**：按清单 URL 下载 → 校验 SHA-256 → 放回本地路径（默认 `tests/fixtures/`，可用 `PDF_FIXTURE_ROOT` 覆盖）；不 commit。
- **基线变更**：任何样本更新必须同时改清单哈希并在 changelog 记录；只改本地文件不改清单视为本地脏数据。
- **CI 口径**：无样本时仅校验清单完整性与 skip 输出，不声称读端回归通过。
- **阶段文件口径**：`stages/` 中以 `tests/fixtures/` 文件为退出标准的条目，按“本地保留样本”理解；仓库无样本时以 `SKIP(missing-sample)` 记录缺口，不得直接勾选完成。

## 6. 排序原则（与路线图同步）

1. **标准优先**：ISO 32000-1 必选/核心（文件结构、xref、流、过滤器、字体、内容流、图形）> 标准可选（注解、表单、透明、OCG、结构树）> 专用标准（3D/多媒体/签名）> 厂商扩展（Adobe ExtensionLevel、`ADBE`、U3D/PRC）。
2. **读端正确性优先于写端覆盖面**：同层内先修复真实文件可读性与错误恢复，再扩展可写特性。
3. **验证独立**：标准特性优先“库写端生成 + 外部主流工具核对”；读端异形文件由外部工具现场生成、只读、不入仓，见本文件 W/R 两层。
4. **不伪造**：外部工具不可用或特性无法真实生成时，记录“未执行/暂缓”，不得用近似结果或自证代替。

## 7. 执行流程

1. 选定用例 → 确认写端是否支持；不支持则先补写端或改为“容器 + 外部码流”。
2. 生成到 `target/fixtures/writer/<case>/`；校验版本戳、`/Producer`、确定性 SHA-256。
3. 按 §2.2 跑 V1–V5，把工具实现、版本、命令、结果写入 `verification.json`；偏差回写矩阵对应行与本文件状态。
4. 读端特性在 R 层执行，结果只留本地清单；发现缺陷时同步 `docs/matrix/` 与 `docs/roadmap/backlog/open-issues.md`。
5. L 层先查清单与本地文件：存在且哈希一致才跑用例；缺失则记 `SKIP(missing-sample)`，不得记为通过；哈希不符记 `FAIL`。
6. 新增或替换任何样本时，先改清单（来源 URL、许可、SHA-256），再把本地文件放回；不得反向“按文件改写哈希”。
7. 每轮结束运行 `scripts/docs_check.ps1 -Strict` 与 `scripts/spec_check.ps1 -Strict`。
