# 读端鲁棒性验证方案（评估与落地顺序）

> 规划层｜职责：评估读端鲁棒性如何独立验证，定义方案取舍、落地顺序与验收判据。｜禁止：复制测试名、记录测试计数/行数/体积、存放历史叙述。

本文回答一个问题：**库里写出的 PDF 再由外部工具核对，只能证明写端与外部读器；读端能否吃下现实世界的异形文件、损坏文件与恶意文件，需要另一套验证。** 本文只做评估与排期，不修改 `src/` 与 `tests/`，也不代替 [fixtures.md](backlog/fixtures.md) 的 W/R/L 分层。

## 0. 结论摘要

1. **先修资源护栏，再谈模糊测试。** 当前读端多数结构遍历已有上限，但仍有四类缺口会让验证被 OOM、栈溢出或超时淹没：流解码输出无上限、XRef 条目按声明数量预分配、公共名称树类型递归无深度/环限制、对象读取窗口固定且不重试。
2. **验证主力应是本库内部可离线执行的判据**：结构感知变异、资源炸弹、错误分类、往返不变量。它们不依赖外部参考实现，能证明“不 panic、不中止、不挂起、错误类型化”。
3. **差分 oracle 按“是否参与自动判定”分层**：自动层仅 qpdf、Apache PDFBox、pdfium、pdf.js；Ghostscript、Poppler、MuPDF、veraPDF 等 GPL/AGPL 工具只作人工核对，不进脚本/CI/判定，缺失不算失败也不记 SKIP。人工核对不能替代自动判据。
4. **资源预算一步到位可配置**：`ReaderLimits` 是唯一库内入口，默认值即 P0.2 表；每项可放宽/收紧，超限统一 `ResourceLimit`，禁止截断返回 `Ok`；打开文档时一次性生效，文档不能篡改。
5. **像素差分当前无法证明本库读端**：本库无光栅化器；渲染器落地前用“解码后图像尺寸/分量 + 页框 + 文本”作代理判据。
6. **不引入 `cargo-fuzz`、AFL、`proptest`**：`cargo-fuzz` 需 nightly，新增测试依赖会触发依赖登记与适配层规则；改用仓库内仅依赖 `std` 的确定性变异器。
7. **推荐顺序**：P0 口径与预算 → P1 资源护栏与窗口/深树缺口 → P2 稳定变异 → P3 生产者语料 → P4 往返属性 → P5 差分 oracle → P6 错误分类覆盖 → P7 持续回归。

## 1. 现有基础与证据

### 1.1 已有测试覆盖

- 既有入仓 L 层样本承担读端冒烟：[fixtures.rs](../../tests/fixtures.rs#L51-L78) 覆盖最小文档、四页 pdflatex 文档、截断文件与单点破坏；内容流、状态机、标记内容、XMP 另有集成覆盖。W 层用例只证明写端产物可读，不是“读端能吃任意外部文件”。
- R 层在 [fixtures.md](backlog/fixtures.md) 中已规划 R-01 至 R-08，状态均为待执行；自动判据层工具均未安装，本次未执行外部语料。
- **新增测试 PDF 一律不入 git 追踪**；入仓只放生成脚本、清单与最小复现方式，产物落 `PDF_FIXTURE_ROOT` 或 `%LOCALAPPDATA%`；既有样本维持现状。
- 缺口：没有模糊、属性、差分、预算与错误分类覆盖测试；现有损坏样本只是点状冒烟。

### 1.2 错误模型与时序

- 文件级致命错误是单一结构 `ParseError { offset, message }`，见 [reader/mod.rs](../../src/core/reader/mod.rs#L16-L24)；当前没有 `kind` 或错误码字段。
- 子模块另有类型化错误（导航 `LimitExceeded`、文本 `TextExtractionError`、页面内容 `PageContentError`、过滤器 `DecodeError`），但顶层没有统一分类。
- 解析是窗口式懒加载：xref 经典表 → XRef 流 → 全文扫描三层回退；对象按需解析并缓存；部分不合规输入记 warning 后继续。
- 库内没有墙钟超时，也没有全局文件大小/总解码量上限；只有各处局部的深度、节点数、流数量与解码字节上限。
- 结论：变异测试目前只能断言“返回 `Err`”，无法机械断言“哪一类错误”。`ParseErrorKind` 已获批准在 P1 加入，P6 直接按类别断言，不再用消息前缀过渡。

这些上限说明读端不是“完全无防护”；问题集中在**上限之外**的解码输出、按声明值预分配、递归路径与窗口边界。

### 1.4 unsafe 面

- [lib.rs](../../src/lib.rs#L1) 是 `#![forbid(unsafe_code)]`，`src/` 内没有 `unsafe` 块。
- 第三方解码 crate 内部可能用 `unsafe`，被适配层隔离在公开 API 之外；本库 `Result` 无法捕获其 panic/OOM/abort，风险仍在第三方实现内部。
- 模糊测试重点是本库与适配层的 panic、溢出、无限递归、OOM、挂起；OOM 会中止进程，`catch_unwind` 无效，必须分配前拦截或子进程隔离。

## 2. 方案空间评估

### 2.1 差分测试（本库 vs 参考实现）

**能证明**：在可执行样本上，本库与参考实现对页数、页框、文本、可确定性解码流、对象可达性等语义一致；能发现“本库接受/拒绝与主流读器不同”的兼容性问题。

**证明不了**：本库无光栅化器，像素差分只能证明外部渲染器或生产者；两套实现共享的规范误解不会被发现；未进入语料的构造、字体、加密、损坏恢复路径不被覆盖；参考实现的恢复策略不是规范，差异需人工分类。

**判定分层（替代“按是否被调用”的论证）**：

- **自动判据层**：qpdf、Apache PDFBox、pdfium、pdf.js。**只有这四者可以进入脚本、门禁或影响 PASS/FAIL**；工具缺失记 SKIP 并写明原因，不默认通过。
- **人工可选层**：Ghostscript、Poppler、MuPDF、veraPDF 等 GPL/AGPL 工具。**不写进任何脚本、不进 CI、不参与判定、结果不入仓、缺失不算失败也不记 SKIP**，只由人工自行核对。
- **人工核对在任何情况下都不得被当作自动判据的替代证据**，包括截图、日志、口头结论与人眼比对。

**许可证与判定（逐项核对官方仓库许可证文件，不凭印象）**：

| 工具 | 官方许可标识（来源） | 层 | 归类理由 |
|---|---|---|---|
| qpdf | Apache-2.0（[LICENSE.txt](https://github.com/qpdf/qpdf/blob/main/LICENSE.txt)） | 自动 | 许可白名单；结构校验 CLI 可脚本 |
| Apache PDFBox | Apache-2.0（[LICENSE.txt](https://github.com/apache/pdfbox/blob/trunk/LICENSE.txt)） | 自动 | 许可白名单；Java CLI 可抽文本/页数 |
| pdfium | BSD-3-Clause AND Apache-2.0（[LICENSE](https://pdfium.googlesource.com/pdfium/+/refs/heads/main/LICENSE)） | 自动 | 两段均白名单；无官方 CLI，需自建 `pdfium_test` |
| pdf.js | Apache-2.0（[LICENSE](https://github.com/mozilla/pdf.js/blob/master/LICENSE)） | 自动 | 许可白名单；Node API 可抽文本/页数 |
| Ghostscript | AGPL-3.0-or-later（[LICENSE](https://github.com/ArtifexSoftware/ghostpdl/blob/master/LICENSE)） | 人工 | AGPL 在工程约定 #1 的拒绝清单 |
| Poppler | GPL-2.0（[COPYING](https://gitlab.freedesktop.org/poppler/poppler/-/blob/master/COPYING) 为 GPLv2 全文） | 人工 | GPL 在工程约定 #1 的拒绝清单 |
| MuPDF | AGPL-3.0（[COPYING](https://github.com/ArtifexSoftware/mupdf/blob/master/COPYING) 为 AGPLv3 全文） | 人工 | AGPL 在工程约定 #1 的拒绝清单 |
| veraPDF | GPL-3.0 与 MPL-2.0 双许可（[LICENSE.GPL](https://github.com/veraPDF/veraPDF-library/blob/integration/LICENSE.GPL)、[LICENSE.MPL](https://github.com/veraPDF/veraPDF-library/blob/integration/LICENSE.MPL)） | 人工 | GPL 选项在拒绝清单；MPL 仅有条件允许，且外部 validator 的发行物默认含 GPL 选项、许可选择需逐发行物确认，不满足自动层的无歧义要求 |

上表按官方仓库许可证文件逐项核对；若某工具的发行物实际许可与此表不符，以发行物为准改记，并说明该工具为何仍归入当前层。

**能力分工**：qpdf 负责页数、页框、目录/页面树可达性、可确定性解码流字节哈希与 `--check` 诊断；PDFBox 负责文本与页数；pdf.js 作文本/页数交叉；pdfium 仅在自建 CLI 可用时作可选交叉。文本比对用 Unicode 归一化 + 空白折叠 + 序列/多重集比对，已知差异（ActualText、连字、OCG 可见性、顺序）进豁免表。像素比对推迟到本库有渲染器。

**冲突点**：外部 CLI 是进程边界，不进入 Rust 依赖图；GPL/AGPL 工具只作人工核对，因此 [principles.md](principles.md) 工程约定 #1 的文本不需要任何修改。

**结论**：差分值得做，但只作本地/可选验证；自动层工具缺失时 SKIP，人工层不产生任何证据；结构差分优先 qpdf，文本差分优先 PDFBox。

### 2.2 真实世界语料（生产者生成 + 公开测试集）

**能证明**：读端能接受不同生产者写出的真实结构（大流、对象流、增量更新、字体子集、混合引用、表单/书签等）；能把“只在真实文件出现的组合”带进变异与差分。

**证明不了**：覆盖所有生产者与所有异形组合；对抗性输入（那是变异/炸弹的职责）。

**方案取舍**：

- **生产者现场生成**：Edge 打印本地 HTML、Word COM 导出 DOCX→PDF、pdfTeX 生成；LibreOffice 缺失则跳过。Ghostscript 仅作人工可选生成，不写进脚本。脚本与清单可入仓，**PDF 不入 git 追踪**，落 `%LOCALAPPDATA%` 或 `PDF_FIXTURE_ROOT`，记录生产者版本与 SHA-256。
- **公开测试套件**：pdf.js 仓库是 Apache-2.0，但其 `test/pdfs` 中 PDF 许可逐文件不同且大量来源不明；pdfium 的 `testing/resources` 同类问题。**不能整包再分发，也不应作为入仓样本**；只能本地下载、逐文件审许可后临时使用，不作为 CI 资产。
- 既有 `py-pdf/sample-files` 的四个样本已按 CC-BY-SA-4.0 入仓并冻结；本方案不再新增此类入仓样本。

**成本与冲突**：Edge/Word/pdfTeX 已安装，脚本可离线；LibreOffice 缺失时跳过。产物不入 git，清单只记元数据；公开测试集不得整包再分发。**结论**：这是投入产出比最高的“现实性”来源，应排在变异测试之后、差分之前。

### 2.3 变异/模糊测试

**能证明**：在语料与变异策略覆盖到的路径上，输入不会导致 panic/abort/栈溢出/挂起；错误是类型化的；能发现越界、整数溢出、状态机死循环、资源泄漏等问题。

**证明不了**：穷尽所有输入；语义正确性；覆盖率之外的路径；与规范的一致性。

**工具取舍**：`cargo-fuzz`/libFuzzer 需 nightly 且引入 `libfuzzer-sys`，AFL/AFL++ 在 Windows 缺少成熟 Rust 集成，`proptest`/`quickcheck` 会新增依赖，三者均**不采用**。改用仓库内确定性变异器：只用 `std`、固定种子、显式算子，可在 CI 离线复现。

**变异策略**：

- 字节级：截断尾部、半截对象、翻转字节、插入垃圾、删除 `endstream`、破坏 xref 偏移、重复/缺失对象。
- 结构感知：把数组/字典嵌套推到上限、构造 `/Kids` 环、构造名称树环、声明超长 `/Length`、构造超长 `/Index`、构造巨大对象号、递归 XObject、内联图像洪水、压缩炸弹。
- 语法感知：改写 `/Filter` 链、`/DecodeParms`、`/W`、`/Index`、`/Size`、`/Prev`，覆盖回退链与降级路径。

**判据**：不 panic、不中止、不超时；`Result` 为 `Ok` 或类型化 `Err`；每个失败都有最小化复现件与归因（本库 / 适配层 / 预算不足）。**成本**：中；无新增依赖，需要子进程隔离、超时与内存上限、最小化器。**结论**：这是读端鲁棒性的主力，必须在 P1 资源护栏之后做，否则 OOM/栈溢出会淹没结果。

### 2.4 资源耗尽与拒绝服务

**能证明**：在给定预算下，炸弹式输入会终止并给出类型化错误，而不是 OOM、abort、长时间占用 CPU。**证明不了**：所有资源路径；预算之外的极端输入；语义恢复能力。

**炸弹目录**：

- 递归/循环 XObject：表单 XObject 自引用、`/Resources` 回指。
- 深层与环：数组/字典、页面树、结构树、名称树、NumberTree、`/Length` 间接引用自环。
- 超长流与压缩炸弹：声明巨大 `/Length`、超窗口流、对象流/XRef 流超过窗口、Flate/LZW 小输入大输出。
- 预分配与数量洪水：XRef 流巨大 `/Index` `count`、全文扫描巨大对象号、海量对象/注解/字体/CMap。
- 图像炸弹：JPEG/JPX/JBIG2 帧头声明的巨大尺寸；内联图像洪水。

**现状缺口（静态证据，需最小样本确认后修复）**：

- Flate 解码 `read_to_end` 无输出上限：[flate.rs](../../src/core/filters/flate.rs#L38-L45)；文本/页面层在解码**之后**才检查 64 MiB，见 [page_content/mod.rs](../../src/core/reader/page_content/mod.rs#L269-L275)，炸弹在检查前已经分配。
- LZW 适配层把解码结果直接写入无上限 `Vec`：[lzw_backend.rs](../../src/core/filters/lzw_backend.rs#L23-L28)。
- DCT 适配层直接调用 zune-jpeg，没有像 JPX 那样的尺寸/输出字节护栏：[jpeg.rs](../../src/core/filters/jpeg.rs#L97-L103)。
- XRef 流按攻击者可控的 `/Index` `count` 预分配：[xref.rs](../../src/core/reader/xref.rs#L238-L258)；全文扫描按最大对象号预分配：[xref.rs](../../src/core/reader/xref.rs#L412-L413)。两者都可能在小文件上直接 OOM。
- 公共 `types::NameTree`/`NumberTree` 递归遍历 `/Kids`，无深度或环检测：[trees.rs](../../src/core/types/trees.rs#L52-L69)；读端导航另走受控 walker（深度 64、节点 4096、环检测），两者需对齐。
- 对象读取窗口固定 64 KiB：[reader/mod.rs](../../src/core/reader/mod.rs#L48)、[document/mod.rs](../../src/core/reader/document/mod.rs#L64-L74)；`compute_stream_range` 要求流终点落在窗口内，注释写着“调用方应扩大窗口重试”，但 `get_object` 没有重试：[lexer.rs](../../src/core/reader/lexer.rs#L384-L397)。静态推断：超过窗口的流对象会被拒收；真实生产者的图像流/内容流经常超过该尺寸，需最小样本实测确认。

**预算模型**：统一见 P0.2；时间/内存由 harness 子进程执行，库内不引入超时线程。**成本与冲突**：部分上限是既有字段扩展，部分需新增公共配置；公共 API 变更需设计默认值与错误语义；上限过严会误拒合法大文件，需以真实语料校准并保留放宽入口；OOM 必须“分配前检查 + 子进程内存上限”。**结论**：这是所有其他验证的前置条件，应作为 P1。

### 2.5 属性/往返测试

**能证明**：读端与写端对同一对象图自洽；`parse → write → parse` 后规范对象图等价；页数、可达性、无悬空引用、确定性过滤器解码哈希稳定。**证明不了**：外部语义正确性；规范条款全部要求；外部生产者文件；共享的规范误解。

**与差分分工**：往返是内部一致性，零外部依赖、便宜、可离线、可高频；差分是外部语义一致，需要参考实现、昂贵、受许可与离线约束。往返先跑，排除读写自相矛盾，差分再聚焦外部差异。

**做法**：同版本重写并规范化比较，忽略对象编号、ObjStm/XRef 流重新打包、`/Length` 重算、`/ID`、日期与字典键序；任何输入不得 panic，写出失败必须是类型化错误，失败后不得留下半截文件；不新增 `proptest`，用确定性生成器与显式不变量。**成本**：低；canonicalizer 必须精心设计，否则噪声会掩盖真实问题。

### 2.6 错误分类覆盖

**能证明**：对定义好的注入点，读端返回预期类别的错误，而不是笼统失败或 panic；错误分类没有盲区。**证明不了**：恢复策略的正确性；所有错误路径；语义等价。

**现状与决定**：`ParseError` 只有 offset/message；消息前缀分类会漂移。`ParseErrorKind` 已获批准，P1 按破坏性改动加入（库未发布），P6 用“注入点 → 期望类别”矩阵统计，不用行覆盖率或前缀。

**成本**：低到中；需要稳定的错误类别与公共 API 变更记录。**冲突点**：`ParseError` 增加字段会破坏结构体字面量构造，P1 在同一增量迁移全部调用点并在 changelog 记录。

### 2.7 补充方案：静态预算审计与崩溃归因

- 静态审计：扫描 `unwrap`/`expect`/整数转换/`with_capacity`/递归点，建立“可 panic/可 OOM/可栈溢出”清单；能证明清单完整性与趋势，不能证明运行时行为。
- 崩溃归因：按错误类别/调用阶段/最小复现件去重；每个修复绑定一个最小回归样本。
- 成本低、离线、无依赖；作为 P2/P6 配套，不单独立项。

## 4. 分层落地顺序

### P0 口径、预算与分类（零外部依赖；本轮只落文档）

**前提修正**：当前 `ParseError` 是 `pub struct ParseError { pub offset: usize, pub message: String }`，不是枚举，也没有可枚举的“现有变体”。因此不能“以 `ParseError` 现有变体为基础”分类；P0 改为“以现有错误来源/子模块类型为基础”，并把 `ParseErrorKind` 列为 P1 的公共改动。

#### P0.1 错误分类口径

新增 `ParseErrorKind`（P1 实现）。分类按“错误发生在哪一层”，资源超限独立成类：

| kind | 现有来源 | 语义 |
|---|---|---|
| `Lexical` | 词法器/头部/EOF | token、字符串、数字、注释、流边界语法错误 |
| `Xref` | `parser`/`xref` | `startxref`、xref 表/流、`/Prev`、trailer、`/Index`、`/W` |
| `Object` | `object` | 间接对象头、字典/数组、对象流、`/Length`、`endstream` |
| `Filter` | `DecodeError` | 过滤器链、参数、预测器、图像解码后端 |
| `Security` | `SecurityError` | 加密字典、口令、密钥、解密/鉴权 |
| `Navigation` | `NavigationError` | Catalog、页面树、页对象、名称树、大纲 |
| `Content` | `ContentStreamError`/`PageContentError` | 内容流算子、资源、状态机 |
| `Font` | `FontError` | 字体字典、CMap/ToUnicode、字形度量 |
| `Structure` | `StructureError::Malformed` | 逻辑结构树、标记内容、角色映射 |
| `Metadata` | `XmpError` | XMP/元数据 XML |
| `ResourceLimit` | 各 `LimitExceeded`/`ContentTooLarge` + 新预算 | 任何超预算，不论发生在哪一层 |
| `Io` | `std::io` 映射 | 文件打开、读取、寻址失败 |
| `Internal` | 无（新增） | 不变量破坏；出现即 FAIL，不用于用户输入 |

映射规则：

- 子模块 `LimitExceeded`/`ContentTooLarge` 一律优先映射为 `ResourceLimit`，不按所在层分类。
- `DecodeError` 中的尺寸/输出超限映射为 `ResourceLimit`，其余映射为 `Filter`。
- `ParseError` 保留 `offset`/`message`，新增 `kind`；P1 提供构造器并迁移调用点。公共结构体字面量构造属于破坏性变更，需在增量中明确记录。

**通过/失败判定**：

- PASS：返回 `Err` 且 `kind` 属于上表（`Internal` 除外）。
- PASS：返回 `Ok` 且 `Document::warnings()` 非空，并通过完整性检查——页数、可达对象、流解码与基线一致，警告文本点名被修复的构造。
- PASS：合法种子返回 `Ok`，页数/文本/预算符合预期，无警告。
- FAIL：panic、abort、非零退出、超时、OOM。
- FAIL：`Ok` + 无警告 + 完整性不成立 = 静默截断；包括页数少于基线、声明 xref 条目不可达、页面缺 `/Contents` 等。
- FAIL：资源炸弹被“成功”打开，但实际未解码或被截断。
- FAIL：期望类别与实际类别不符；未知类别或 `Internal`。
- FAIL：同一输入两次运行结果不一致（非确定性）。

#### P0.2 资源预算表（默认值即上限，超限一律 `ResourceLimit`）

**配置结构**：`ReaderLimits` 是唯一库内入口，由 `Document::open_with_limits` / `Parser::open_with_limits` 接收；打开文档时复制为只读快照，同一文档的所有子模块共用该快照，之后调用方再改配置不影响已打开文档。字段使用 `NonZeroUsize` 或显式 `usize` + 校验，不设“0 = 无限”。默认值由 `ReaderLimits::default()` 提供，现有常量降级为默认值来源，不再散落硬编码。全部字段可放宽或收紧；未覆盖字段取默认值。

**作用层**：库内预算在打开文档时一次性生效；文件大小在打开后、首次窗口读取前拦截；页面数在页面树遍历中累计；对象总数在 xref 合并/全文扫描中拦截；解码预算在分配前/分配中检查；累计解码在每次流解码时累加。时间与内存由 harness 的 `RunBudget`（墙钟、RSS）在每次子进程运行时一次性读取，不传入库；其默认值与本表一致。

**不可篡改**：所有限制值是宿主代码里的 Rust 值。解析器从不把 PDF 字典、流、xref 中的数字写入限制；被解析文档只能让 observed 值增大，不能修改 allowed 值。库内不存在从 PDF 读取的“上限键”。

| 项目 | 默认上限 | 依据 | 配置 |
|---|---|---|---|
| 文件大小 | 1 GiB | 工程取舍：覆盖常见扫描/CAD；文件 + 解码峰值可在 3 GiB 进程预算内 | 可放宽/收紧 |
| 对象总数 | 1,048,576 | xref 条目按 40 B 估算约 40 MiB；足以覆盖大型长文档，超出属异常 | 可放宽/收紧 |
| 对象号 | ≤ 2^31−1（规范） | 规范上限；按稀疏存储，禁止按最大号预分配 | 规范固定，可收紧 |
| xref 段数 | 64 | 现有 `/Prev` 深度 | 可放宽/收紧 |
| 页面数 | 65,535 | 2^16−1；每页至少约 2 个对象，仍在对象预算内 | 可放宽/收紧 |
| 页面树节点 | 131,071 | 二叉页面树节点上限 ≤ 2N−1，与页面数联动 | 可放宽/收紧 |
| 单流原始字节 | 512 MiB | 单对象不应占满整个文件预算；避免一次性读入挤占内存 | 可放宽/收紧 |
| 每页内容流解码 | 64 MiB | 现有 `MAX_CONTENT_BYTES`；典型内容流远小于此 | 可放宽/收紧 |
| 每页内容流数 | 4096 | 现有 `MAX_CONTENT_STREAMS` | 可放宽/收紧 |
| 图像解码输出 | 256 MiB，单边 ≤ 65,536 | 现有 JPX/JBIG2 适配层口径；256 MiB ≈ 8192²×4 B | 可放宽/收紧 |
| 其他流解码 | 64 MiB；ObjStm/XRef 流放宽到 256 MiB | 字体/XMP 等小流；对象流可能承载大量对象 | 可放宽/收紧 |
| 文档累计解码 | 1 GiB | 4 个图像预算，防止多流叠加 | 可放宽/收紧 |
| 文档流总数 | 65,536 | 与对象数/页面数同量级，防止流洪水；累计解码量才是主约束 | 可放宽/收紧 |
| 对象嵌套 | 64 | 现有；现实文档远低于此，栈深度安全 | 可放宽/收紧 |
| 表单 XObject 深度 | 32 | 现有 | 可放宽/收紧 |
| 页面树深度 | 64 | 现有 | 可放宽/收紧 |
| 名称/编号树深度、节点 | 64、4096 | 现有导航 walker；公共 `types::NameTree` 需对齐 | 可放宽/收紧 |
| 结构树深度、元素 | 64、4096 | 现有 | 可放宽/收紧 |
| 大纲深度、条目 | 64、10,000 | 现有 | 可放宽/收紧 |
| 文本/图形状态深度 | 256 | 现有 | 可放宽/收紧 |
| OC 重定向深度 | 16 | 现有 | 可放宽/收紧 |
| xref `/Index` 计数 | 1,048,576 | 与对象总数一致；禁止按声明值直接 `with_capacity` | 可放宽/收紧 |
| 时间（harness） | Tier S（≤16 MiB）：解析 5 s、全读 60 s；Tier L：解析 1 s+20 ms/MiB（cap 60 s）、全读 5 s+100 ms/MiB（cap 300 s） | 工程取舍：按 10 MiB 样本解析约 1.2 s、全读约 6 s 的 CI 目标反推 | 可放宽/收紧（外层） |
| 内存（harness） | Tier S 1 GiB；Tier L 512 MiB+1×文件（cap 3 GiB） | 进程隔离；覆盖解码峰值 | 可放宽/收紧（外层） |

行为：

- 所有超限返回 `ResourceLimit`，消息包含 `limit=<名称> observed=<值> allowed=<值>`；**不截断后返回 `Ok`**。
- 放宽风险由调用方承担；收紧用于不可信输入场景。配置变更属于调用方显式行为，不从文档推断。
- 时间与内存由外层 harness 强制，库内不引入超时线程，也不产生 `Timeout` kind；harness 超时/超内存记为 FAIL。

#### P0.3 语料清单与通过判据

| 种子类 | 来源 | 期望结果 |
|---|---|---|
| S0 合法 L 层 | 现有入仓样本 | `Ok`；页数与基线一致；文本非空；warnings 为空 |
| S1 合法 W 层 | 写端生成，覆盖页面树/内容/字体/注解/表单/XMP/图像 | `Ok`；页数与基线一致；对应特性可读 |
| S2 生产者 | Edge/Word/pdfTeX 现场生成；LibreOffice/GS 按政策可选 | `Ok`；页数以外部工具为准（缺失时用基线）；所有流在预算内；文本/图像按预期非空 |
| S3 硬损坏 | 手工构造：截断、坏 xref、坏 `/Length`、坏 `/Filter`、页面树环、名称树环 | 类型化 `Err`，或带警告的显式恢复；不得静默成功 |
| S4 资源炸弹 | Flate/LZW 压缩炸弹、巨大 `/Index`、巨大对象号、深嵌套、递归 XObject、巨幅 JPEG | `ResourceLimit`；不得 panic/OOM/超时 |
| S5 截断梯度 | 每个种子在 5%、25%、50%、75%、95% 处截断 | 类型化 `Err` 或带警告恢复；不得静默丢失页面 |
| S6 字节翻转 | 每个种子最多 16 个偏移 × 8 个位（上限 128 个变异体） | 无崩溃；结果按“类型化拒绝 / 显式恢复 / 仍合法”归类 |

通过率口径：

- panic、abort、OOM、超时：**0 容忍**。
- S3/S4/S5：预期结果符合率 **100%**；其中 S4 的 `ResourceLimit` 命中率 **100%**。
- S6：无崩溃 **100%**；结构破坏子集的类型化拒绝率 **≥95%**；其余必须归入“仍合法”或“显式恢复”，未分类结果 **0**。
- S0/S1/S2：`Ok` **100%**；除非种子显式标注允许警告，否则 warnings 为空。
- 整体静默截断：**0**。

语料清单字段：`id`、类别、来源、生产者/版本、生成命令、SHA-256、许可/版权、期望结果（`Ok(page_count, warnings)` 或 `Err(kind)`）、外部队列检查、未执行原因。**清单入仓，PDF 不入 git。**

#### P0.5 P1 改动清单与验收

**横切载体**：`ParseErrorKind` + `ReaderLimits` + 子模块错误映射。验收：每个注入点命中期望 kind；资源超限统一 `ResourceLimit`；公共 API 变更记录完整。

**缺口一：64 KiB 读取窗口（先做最小样本实测）**。样本：内容流、图像流、ObjStm、XRef 流各一个明显超过 64 KiB 的文件。先确认当前是否被拒，再决定“扩大窗口重读”还是“按原始字节预算拒绝”。验收：预算内可读并能抽取文本/流字节；超预算返回 `ResourceLimit`，不得泛化报错或静默截断。

**缺口二：解码输出与统一预算**。Flate/LZW/DCT 在分配前/中设上限，与 CCITT/JPX/JBIG2 的 256 MiB 对齐；同时落地页面数、页面树节点、对象总数、累计解码与流总数预算。验收：压缩炸弹、巨幅 JPEG、海量流在 Tier S 内终止并返回 `ResourceLimit`；RSS 不超 1 GiB。

**缺口三：XRef 预分配**。`/Index` 计数与全文扫描最大对象号不得按声明值分配；改稀疏存储 + 预算检查。验收：小文件构造巨大 `/Index`/对象号，RSS 不超 1 GiB，返回 `ResourceLimit`，不得 OOM。

**缺口四：名称树/NumberTree**。公共 `types::NameTree`/`NumberTree` 与导航 walker 统一为显式栈迭代，补深度、节点数与环检测。验收：环、深树、海量 `/Kids` 返回类型化错误；不得栈溢出；导航行为不回归。

执行顺序：先确认 64 KiB（决定真实语料能否读，且唯一需先实测再定修复方式）；再做解码/预算；随后修 XRef 预分配；最后收敛名称树公共 API。P1 完成后按项目规则跑全量 `cargo build/test/clippy` 与既有脚本，零警告、全绿；本文不先行修改 [principles.md](principles.md)。

### P1 资源护栏与窗口/深树缺口（前置修复，另立 `src/` 增量）

**`ParseErrorKind` 兼容策略（已批准，按破坏性改动推进）**：

- `ParseError` 增加 `pub kind: ParseErrorKind`，保留 `offset`/`message`；提供 `ParseError::new(kind, offset, message)` 与只读访问器，所有构造点在同一增量迁移。
- `ParseErrorKind` 为 13 个变体的公开枚举，加 `#[non_exhaustive]` 以便后续新增类别；仓内匹配补全通配分支。
- 不提供弃用兼容构造器、`Default`、消息前缀分类或“kind + 前缀”双表示；库未发布，不承诺 SemVer 兼容，变更记入 changelog 与公共 API 说明。
- P6 直接按 `kind` 断言；过渡期消息前缀方案取消。

**四项缺口**：

- Flate/LZW/DCT 增加分配前/中的输出上限，与 JPX 的尺寸/输出上限对齐。
- XRef 流 `/Index` 与全文扫描对象号增加预分配上限；超限返回类型化资源错误。
- 名称树/NumberTree 与导航 walker 统一为显式栈迭代，加深度、节点数与环检测。
- 对象窗口按声明长度/文件长度放大并重试；或给出上限内的可读策略；超限返回资源错误。

**为什么先做**：这是 P2/P3 的前置条件；先跑变异会反复撞同一批 OOM/栈溢出，先跑真实语料会因大流被拒产生大量假失败。

**验收判据**：

- 超窗口的内容流、图像流、对象流/XRef 流在预算内可读，或按声明上限返回类型化资源错误。
- 压缩炸弹、巨大 `/Index`/对象号、名称树环在预算内终止并返回类型化错误，不 panic/OOM/栈溢出。
- DCT 与 JPX/JBIG2 的尺寸/输出预算行为一致。
- 按项目规则完成全量 `cargo build/test/clippy` 与既有脚本验证（本任务不执行）。

### P2 稳定变异 harness（离线，无外部 oracle）

**做什么**：建立仅用 `std` 的确定性变异器：固定种子、显式算子、语料来自 L/W/R；每个输入在子进程中解析、遍历页面、抽取文本、解码流，带墙钟超时与内存上限；失败按类别与位置去重并最小化；CI 冒烟 + 本地/夜间长跑；**生成器与最小复现方式入仓，PDF 不入 git**。

**为什么在 P2**：不需要外部工具，直接回答“本库读端会不会崩/挂”，是投入产出比最高的读端专属验证。

**验收判据**：全部变异样本无 panic、无 abort、无超时；`Ok` 或类型化 `Err`；每个失败都有最小复现件、类别归因与修复状态；同类根因不重复刷屏；离线可复现。

### P3 生产者语料（本地生成、不入 git）

**做什么**：用已安装的 Edge 打印、Word COM 导出、pdfTeX 生成；LibreOffice 缺失则跳过，Ghostscript 仅人工可选且不写进脚本。覆盖大流、对象流/XRef 流、增量更新、混合引用、字体子集、表格/链接/书签、图像；每个生产者至少一条基线。记录生产者版本、命令、SHA-256、内容版权；**文件落本地，不入 git**。

**为什么在 P3**：P1 保证大流可读后，生产者语料才能提供真实结构；它又是 P2 语料与 P5 差分的输入源；成本低于安装外部读器。

**验收判据**：每个生产者样本文件级解析成功；页数与本库遍历结果一致；所有流在预算内解码；应出文本/应出图像的样本不空；失败件有最小复现与归因；工具缺失时明确跳过，不伪造“通过”。

### P4 往返属性（离线，复用 P2/P3 语料）

**做什么**：对可接受语料执行同版本重写与再解析；用 canonicalizer 比较对象图与结构不变量（页数、引用可达性、确定性过滤器解码哈希、页框、注解/大纲等已支持模型）；把差异分为规范化豁免、已知写端限制、读端缺陷，后两类必须绑定回归样本。

**为什么在 P5 差分之前**：零外部依赖、便宜、可离线；先排除“读端与写端自相矛盾”，再让差分专注外部语义差异。

**验收判据**：全部可接受样本 `parse → write → parse` 不 panic；规范化差异为空或落在有书面理由的豁免表；任何新增差异都有最小复现件与归因。

### P5 差分 oracle（自动判据层本地/可选，不作为默认 CI 门禁）

**做什么**：

- 结构差分用 qpdf：页数、页框、目录/页面树可达性、可确定性解码流的字节哈希、`--check` 诊断。
- 文本差分用 PDFBox，pdf.js 作交叉；Unicode 归一化 + 空白折叠 + 序列/多重集比对；已知差异（ActualText、连字、OCG 可见性、顺序）进豁免表。
- pdfium 仅在自建 CLI 可用时作可选交叉；不可用则记 SKIP。
- 图像差分：本库无渲染器，暂不做像素比对；比较解码后的尺寸/分量/位深，并与自动层工具对照。
- 每条差异分类为“本库缺陷 / 参考实现差异 / 规范未定义 / 已知豁免”；未分类差异不得通过。

**人工层边界**：Ghostscript、Poppler、MuPDF、veraPDF 不写进本节的任何脚本，不产生 PASS/FAIL、不入仓、缺失不记 SKIP；人工核对结果不得作为自动判据的替代证据。

**为什么在 P5**：外部工具未安装、许可与离线约束最强；需要 P1 的稳定接受与 P3 的多样输入才能减少噪声。它证明“与主流读器一致”，不是“不崩”，因此排在内部判据之后。

**验收判据**：可执行的每条样本都有结论（一致 / 已知差异（有理由） / 缺陷），未分类差异为 0；自动层工具缺失记 SKIP + 原因，不默认通过，差分结果不阻塞离线 CI；像素级差分记为“待渲染器落地后另行立项”。

### P6 错误分类覆盖（依赖 P2/P3 语料与 P0 口径）

**做什么**：建立“注入点 × 期望错误类别”的覆盖矩阵；注入点覆盖词法、xref、对象、流/过滤器、加密、页面树、字体、内容、资源上限、IO；断言预期类别命中、无 panic、无超时，未分类错误数为 0；直接断言 `ParseErrorKind`，不使用消息前缀。

**为什么在 P6**：它衡量“错误是否可区分”，需要 P2/P3 产生的失败样本与 P0 的分类口径；过早做会得到空洞的矩阵。

**验收判据**：每个注入点映射到预期类别；未分类错误为 0；资源类与语法类可区分；类别在回归中稳定；覆盖统计以注入点矩阵呈现，不以行覆盖率代替。

### P7 持续回归

**做什么**：每个修复绑定最小样本；变异与语料回归集只增不减（除非证明重复）；本地/夜间长跑；发版前跑一次自动层差分并记录版本与结果。

**验收判据**：同类缺陷不复发；新增样本可追溯到来源与许可；差分记录可复现。

## 5. 明确不做 / 推迟

- `cargo-fuzz`、libFuzzer、sanitizer：与“禁止 nightly”冲突。
- AFL/AFL++ 原生 Windows 集成：工具链不成熟，收益不抵成本。
- `pdfium-render`/`lopdf`/`mupdf` 等 Rust crate 或 FFI：违反依赖适配层与离线约束，并可能引入 unsafe。
- 像素级差分：本库无渲染器，当前无法证明读端；等渲染器落地再立项。
- 公开 PDF 测试集整包入仓：许可不可控，且测试 PDF 一律不入 git。
- `catch_unwind` 兜底 OOM：OOM 是进程中止，不是可捕获 panic；必须靠预算与子进程隔离。
- 以行覆盖率或“变异样本数量”作为完成标准：本方案以“注入点类别覆盖 + 无崩溃/无挂起 + 预算内终止”为标准。

## 6. 风险与前置判断

1. **超大流被拒收（静态推断，最高优先级待确认）**：如果最小样本证实 64 KiB 窗口不重试，大量真实 PDF 的图像流/内容流/IPC 流都会被拒；这会直接推翻“读端能吃现实文件”的结论。P1 的第一个验收样本应是明显超过窗口的内容流与图像流。
2. **预分配炸弹**：`/Index` 与全文扫描对象号的 `with_capacity` 可被小文件触发 OOM；应在 P1 用子进程内存上限验证。
3. **名称树递归**：环或深树会栈溢出；应在 P1 改为显式栈迭代并加环检测。
4. **解码输出无上限**：Flate/LZW/DCT 的炸弹会先分配后检查；P1 必须在分配前拦截。
5. **错误类别**：`ParseErrorKind` 已获批准，P1 直接加入字段并迁移调用点；风险转为“映射是否准确”，由 P6 注入点矩阵验收。
6. **自动层工具不可用**：本机 qpdf/PDFBox/pdfium/pdf.js 均未安装或不可直接调用；差分只能本地按需安装，缺失记 SKIP，不能作为 CI 必过项。
7. **许可证与人工层**：Ghostscript/Poppler/MuPDF 为 AGPL/GPL，veraPDF 为 GPL-3.0 与 MPL-2.0 双许可；四者一律只作人工核对，不进脚本与判定，工程约定 #1 文本无需修改。
